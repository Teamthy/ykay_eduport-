# 04 — CBT: 15,000 questions, and the engine that can carry them

Goal: a question bank an exam can be *decided* from — 15,000 published, tagged,
reviewed items — plus a sitting engine that survives a hall full of students on
school wifi.

---

## 1. What exists today (measured)

| Piece | State |
|---|---|
| Bank | **5,483 questions**, `prisma/cbt-bank.csv` (3.1 MB), 4-option MCQ, `difficulty 1–3`, `source` (`curriculum`/`waec-style`/…), `status` (`draft`/`reviewed`/`published`) |
| Models | `CbtSubject` (slug, classLevel, department), `CbtQuestion`, `CbtAttempt` (score, answers JSON) |
| Tenancy | **None.** `CbtSubject` / `CbtQuestion` have no `schoolId` → they are *invisible* to `npm run check:tenant-coverage`, which only looks at models carrying `schoolId`. A second school on the same database would share and could edit Ykay's bank. |
| Engine | `lib/cbt.ts` (79 lines): `gradeAttempt`, `shuffled`, `PublicQuestion` (correct answer withheld — good) |
| Import | `lib/question-import.ts` (435 lines) + `lib/question-parser.ts`: XLSX, DOCX, TXT, CSV |
| School exams | Separate, tenant-scoped engine: `lib/exams.ts`, `Exam`/`ExamQuestion`/`ExamAttempt`/`ExamAnswer`/`ExamRetake`, sitting windows, retakes |
| Seed | `prisma/cbt-seed.ts`, `npm run cbt:seed` |

Reality check on the current bank: sample rows are generated-style arithmetic
("Add: 242 + 323") with templated explanations that even contain a wrong clause
in the distractor commentary. It is **volume, not yet a bank**. Treat the
existing 5,483 as seed scaffolding, and re-review before publishing.

---

## 2. The honest headline: 15k is a content problem, not a code problem

The engine already grades and serves questions. What is missing is 15,000 items
a teacher would defend in front of the exam board, each mapped to the syllabus,
each reviewed by a second person. Code touches perhaps 5–10% of this section's
effort.

Work the arithmetic before promising a date:

| Input | Example value (fill with the school) |
|---|---|
| Subjects | 10 (JSS maths/English/basic science/business studies + SS maths/English/biology/chemistry/physics/economics) |
| Items per subject | 1,500 |
| Topics per subject per class level | ~25–35 |
| Items per topic | ~45–60 |
| Writers, items/day each (realistic, quality-gated) | 40–60 |
| Reviewers | 1 per 4 writers |
| **Throughput** | 6 writers × 50 = **300/day** → 15,000 ≈ **50 working days** of drafting, plus review loop |
| **Calendar** | ~10–14 weeks with review, corrections and re-work |

**Cost model inputs (put real numbers from the school in, not guesses):**
writer rate per accepted item, reviewer rate per item, subject-lead fee,
proofreading, and a contingency of ~15% for re-work. Compare against commercial
JAMB/WAEC practice-question banks — they usually *cannot* be licensed for
redistribution, and copying them is a copyright problem (see §6).

**Do not author down to a date.** A published bank with wrong answers destroys
parent trust in one sitting; a bank of 10,000 clean items beats 15,000 with 300
bad keys. Gate publication on review, always.

## 3. Authoring pipeline (the deliverable)

Build on the existing importer; do not invent a new format.

```
brief (syllabus, class level, exam body, difficulty mix, count per topic)
  → writer drafts in the XLSX template (existing parser reads it)
  → import with --dry-run --report           ← NEW: validator + report, nothing written
  → staging: status = draft, sourceCredited, writer, batchId
  → validator gate     (see §4)              ← NEW
  → subject-lead review (status = reviewed, reviewerName + reviewedAt required)
  → publication gate   (status = published)
  → usage → item analysis → retire/repair    ← NEW
```

Required additions:

- **`scripts/cbt-import.ts --dry-run --report=out.csv`** — reads the same CSV/XLSX
  the parser already handles, validates, prints per-row errors and a summary
  (accepted / rejected / duplicate / needs-review), writes nothing until
  `--commit`. Batch ids so a bad batch can be rolled back (`--rollback=<batchId>`).
- **Validator rules** (each a named failure): exactly 4 non-empty options;
  `correctIndex` in 0..3; no duplicate options within an item; stem length
  bounds; no "all of the above"; explanation present and ≥ 20 characters;
  difficulty in 1..3; topic present and **present in the syllabus map**;
  classLevel/department valid; no HTML/script; no smart-quote/encoding damage;
  no placeholder text; and language/readability sanity for JSS.
- **Duplicate detection**: normalised stem hash (strip punctuation/whitespace/
  numerals) exact match **plus** trigram similarity ≥ 0.9 against the same
  subject/topic. 15,000 hand-written items *will* contain duplicates; catch them
  at import, not after a student sees the same question twice in one paper.
- **Review UI** (`/admin/cbt/review`): keyboard-first (approve / edit / reject /
  reassign / next), shows the duplicate cluster and similar items, bulk approve by
  filter, reviewer stats, and an SLA view ("oldest unreviewed in each subject").
  This screen is what makes 15,000 items tractable — invest in it.
- **Syllabus map** — a real table, not a string:
  `SyllabusNode(subjectId, classLevel, examBody, code, title, parentId, objectives Json)`.
  Every item points at a node. This is what makes topic-level mastery reporting,
  "revise your weak topics" and coverage gaps ("40% of Chemistry SS2 has no
  items") possible at all.

## 4. Schema deltas

```prisma
enum CbtBankScope { PLATFORM  SCHOOL }   // shared curated bank vs school-private bank

model CbtSubject {
  // ...existing...
  schoolId  String?        // null = platform bank, set = school-owned
  scope     CbtBankScope   @default(SCHOOL)
  board     String?        // WAEC | NECO | JAMB | BECE | internal
  @@unique([schoolId, slug])   // replaces the global @unique(["slug"])
}

model CbtQuestion {
  // ...existing...
  schoolId      String?   // mirrors CbtSubject.schoolId (denormalised for RLS + query speed)
  syllabusNodeId String?
  stemHash      String    // duplicate detection
  writerName    String?
  reviewerName  String?
  reviewedAt    DateTime?
  version       Int       @default(1)
  publishedAt   DateTime?
  usageCount    Int       @default(0)
  correctRate   Float?    // filled from attempts — item analysis
  discrimination Float?   // point-biserial-ish; flags ambiguous items
  retiredAt     DateTime?
  retiredReason String?
  @@index([schoolId, subjectId, status, difficulty])
  @@index([schoolId, stemHash])
  @@index([syllabusNodeId])
}

model CbtSitting {          // one candidate's paper = a session, not a loose attempt
  id             String   @id @default(cuid())
  schoolId       String?
  examId         String?                 // links to the school Exam engine when proctored
  studentUserId  String?
  kind           String                  // practice | mock | exam
  bluePrint      Json                    // the sampling spec actually used
  seed           String                  // deterministic shuffle → identical replay
  startedAt      DateTime  @default(now())
  deadlineAt     DateTime                // SERVER-authoritative
  submittedAt    DateTime?
  submissionKey  String    @unique        // idempotent submit (client retries)
  status         String    @default("active") // active | submitted | expired | void
  answers        Json                     // autosaved incrementally
  @@index([schoolId, status, deadlineAt])
  @@index([studentUserId, startedAt])
}
```

**Tenancy fix, non-negotiable:** CBT tables must be included in
`scripts/check-tenant-route-coverage.ts` — extend that script's tenant-model
detection so `schoolId`-nullable models are covered too, and add RLS policies for
`cbt_*` tables. Today a school #2 on the same DB could read or edit the platform
bank; with a separate DB (D1-B) the risk is contained, but the moment you go
multi-tenant it is the first thing that breaks.

## 5. Exam engine at scale

- **Server-authoritative timing.** The client timer is a display. `deadlineAt` is
  set at start and enforced on every answer/save/submit call; late submissions are
  recorded and flagged, not silently accepted.
- **Autosave.** Debounced answer save (per question), resumable after a browser
  crash or a dead battery. A student losing 40 minutes of answers to a power cut
  is a support incident you will get weekly without this.
- **Idempotent submit.** `submissionKey` + the repo's existing
  `IdempotencyRecord` pattern: double-tap or retry never double-grades.
- **Sampling without `ORDER BY random()`.** At 15k items that is a full sort per
  candidate. Use a blueprint spec (per-topic counts × difficulty mix) resolved by
  indexed queries with a per-sitting seed, or a pre-materialised question-slot
  table. Store the blueprint and seed on the sitting — you must be able to prove
  exactly which items a candidate saw, five years later, during a result dispute.
- **Anti-collusion basics** (worth more than proctoring gadgets at this scale):
  per-candidate shuffle order, multiple paper variants per sitting, candidate
  seating maps, "cannot start two sittings simultaneously" constraint, and
  question-exposure caps so the same item is not in every variant.
- **Proctoring, staged.** Stage 1: tab-switch/visibility events + full-screen
  lock + per-sitting log (cheap, no consent burden, catches casual cheating).
  Stage 2: camera snapshots on the school-scoped `Exam` engine only, with written
  consent and the existing route-scoped CSP camera grant. Stage 3 (only if the
  school insists): lockdown browser / supervised hall with device check-in — a
  process, not a feature.
- **Offline hall mode (optional, high value in Nigeria):** pre-fetch the whole
  paper to the device on start (questions contain no answer key — `PublicQuestion`
  already enforces that), accept answers offline, sync on reconnect with
  server-side plausibility checks (duration, monotonic timestamps, submission
  before or shortly after `deadlineAt`). Ship this only after autosave and
  idempotent submit are proven.
- **Reporting**: per-topic mastery, percentile vs. cohort, time-per-question,
  flagged/ambiguous items, per-class and per-teacher view, and a "weak topics
  to revise" study plan that feeds the practice mode.
- **Retention/growth**: at 3,000 users × 4 papers/term, `CbtAttempt`/`CbtSitting`
  grows fast (order 10⁵–10⁶ rows/year). Partition or archive by academic session
  after two sessions; keep aggregates forever so trends survive the delete.

## 6. Legal and quality guardrails

- **Do not bulk-copy WAEC/NECO/JAMB past questions.** Those papers are
  copyrighted; redistributing them commercially is a live risk in Nigeria, and
  schools do get letters. Write **original items in the style** of the exam
  bodies (the `source` field should say `waec-style`, not `waec`), credit
  non-copyright sources (dedicated textbooks with permission, government
  syllabi — syllabi are usually freely licensable but verify per body), and
  record the writer/reviewer identity on every item so provenance is provable.
- **Never publish an item without a reviewer.** The schema enforces it
  (`reviewedAt`, `reviewerName`); the import gate should too.
- **Item analysis is the quality loop**: items with correct-rate < 20% or > 95%,
  or near-zero discrimination, go to a repair queue, not silently into papers.
- **Answer-key disputes need a trail**: who wrote it, who reviewed it, when it
  was published, which sittings used it, and what changed after — hence
  `version`, `publishedAt`, `usageCount`.

## 7. Definition of done

- [ ] ≥ 15,000 items `published`, each with writer + reviewer + syllabus node; zero items published without review.
- [ ] Validator rejects the documented bad-input cases (unit-tested), and a dry-run report is produced for every batch.
- [ ] Duplicate detection catches exact and near-duplicate stems; report reviewed and acted on.
- [ ] CBT tables are tenant-scoped, covered by RLS, and **included in** `npm run check:tenant-coverage`.
- [ ] Blueprint sampling produces the intended topic/difficulty mix (asserted in tests), with no `ORDER BY random()`.
- [ ] Sitting is resumable, timing is server-enforced, submit is idempotent; all three covered by tests.
- [ ] One real school examination sat end-to-end by a full class, with results reviewed against manual marking for a sample of papers (target: zero key discrepancies).
- [ ] Coverage report shows no examinable topic below the agreed minimum item count.
- [ ] Item-analysis job runs after each sitting window; repair queue exists and is worked.
